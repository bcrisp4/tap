# M10 — Offline + PWA

**Status:** Draft, awaiting review.

## Context

Tap is the self-hosted feed reader described in [`../concept.md`](../concept.md). M10 is the tenth of twelve milestones — see [`../roadmap.md`](../roadmap.md). M1–M9 have shipped: the walking skeleton, sanitisation pipeline, media proxy, polling discipline, article extraction, auth foundations, 2FA + passkeys + per-user data isolation, SPA polish, and categories/OPML/search are all in place.

M10 delivers the offline-first reading layer and PWA installability described in concept §6.12 and §13. After M10, the app boots offline, recently-cached entries remain readable when the Go server is unreachable, and state-changing mutations made while offline are queued in `localStorage`, survive a full browser reload, and drain automatically on reconnect or after re-authentication.

M3's proxy URLs already carry `Cache-Control: public, max-age=31536000, immutable` — the service worker can cache-first them without any Go-side changes. M6's CSRF token lives in the session and requires careful handling on queue replay. M7's per-user data isolation means each user's SW caches and mutation queue are keyed by user ID and cleared on logout.

M10 is **entirely frontend**. No new Go packages, no new API routes, no new migrations.

## Goal

After M10, a user can:

1. Load the unread list and open a few entries while online.
2. Close the laptop lid, lose connectivity, and reopen the browser.
3. Navigate the app offline: the shell loads, the cached entry list renders, previously opened entries are readable including their proxied images.
4. Mark entries read and toggle saved while offline — those mutations are queued and replayed automatically when connectivity returns.
5. If the session expired while offline, the queue is preserved; after re-login it drains automatically.
6. Install the app to their home screen (PWA standalone mode, themed status bar, maskable icons).

### New files


`vite-plugin-pwa` is added to `web/package.json`. It compiles `sw.ts` via `injectManifest` mode (the SW is hand-written TypeScript; the plugin injects only the precache manifest and handles the update lifecycle). The PWA manifest is generated by the plugin from config in `vite.config.ts`.

### Service worker: `web/src/sw/sw.ts`

Written in TypeScript, compiled by `vite-plugin-pwa` in `injectManifest` mode. Uses Workbox strategy classes imported directly.

#### App shell (precache)

`vite-plugin-pwa` injects the precache manifest at build time. All files in `web/dist` — JS bundles, CSS, fonts, `index.html` — are precached on SW install. Navigation requests fall back to `index.html` so the app boots offline for any deep-linked route.

#### Entry list endpoints (stale-while-revalidate)

URL pattern: `/api/v1/entries*` and `/api/v1/subscriptions*`.

Strategy: `StaleWhileRevalidate`. Serve from cache immediately; update cache from network in the background. Cache name: `tap-api-{userId}` — per-user so that logout can delete exactly this user's cache. Cache expiry: 200 entries max, 7 days TTL (Workbox `ExpirationPlugin`).

#### Proxy URLs (cache-first)

URL pattern: `/api/v1/proxy/*`.

Strategy: `CacheFirst`. M3 already sets `Cache-Control: immutable` so the SW never revalidates. Cache name: `tap-proxy-{userId}`. Cache expiry: 500 entries max, 30 days TTL. On a cold miss the SW fetches from the Go proxy, which in turn fetches from the origin and caches on the filesystem as before — the SW layer adds a second in-browser cache that survives the Go server being unreachable.

#### Everything else passes through

All non-GET requests (mutations, OPML import, auth) pass through the SW without caching. `GET /api/v1/search*`, `GET /api/v1/opml`, and `GET /api/v1/sessions*` are excluded from caching — search results are volatile and OPML export is not useful offline.

#### Per-user cache naming

The SW receives the user ID from the app via `postMessage` immediately after `auth.bootstrap()` resolves. Until the user ID is received, the SW does not cache any API responses (it still serves precached shell assets). On logout, the app posts a `{type: 'logout', userId}` message; the SW deletes `tap-api-{userId}` and `tap-proxy-{userId}`.

```ts
// workerTypes.ts — shared between sw.ts and app
export type SWMessage =
  | { type: 'set-user'; userId: number }
  | { type: 'logout'; userId: number };
```

#### SW update lifecycle

When a new SW version is available, `vite-plugin-pwa` surfaces an `updateSW` callback. The app registers an `onNeedRefresh` handler that stores the callback and sets a reactive flag. `App.svelte` renders a fixed top-of-viewport banner: "Update available — reload to get the latest version." with a single "Reload" button. The banner is fixed to the top so it does not collide with M8's mobile bottom tab bar.

### Mutation queue: `web/src/lib/offlineQueue.ts`

The queue is the persistence layer for state-changing actions made while offline.

#### Storage format

`localStorage` key: `tap:queue:{userId}`. Value: a JSON array of `QueuedMutation` objects.

```ts
type QueuedMutation = {
  id: string;         // crypto.randomUUID() at enqueue time
  method: string;     // 'PATCH' | 'DELETE'
  path: string;       // e.g. '/api/v1/entries/42'
  body: unknown;      // JSON-serialisable payload
  csrfToken: string;  // CSRF token current at enqueue time
  enqueuedAt: number; // unix ms
};
```

#### Enqueue

Called by `api.ts`'s `request()` function when a non-GET request fails with a network error or when `navigator.onLine === false` at the time of the call. The optimistic store update has already fired. The enqueued mutation preserves the CSRF token from `auth.csrfToken` at the moment of enqueue.

`offlineQueue.enqueue(userId, mutation)` appends to the array and writes back to `localStorage`.

#### Drain

`offlineQueue.drain(userId)` runs serially (one mutation at a time, in order). Called from two places:

1. In `App.svelte`, on the `online` DOM event.
2. In `App.svelte`, after `auth.bootstrap()` resolves with a live user (covers the reload-with-pending-queue case).

Per-mutation error handling:

| Server response | Action |
|---|---|
| 2xx | Dequeue, continue |
| `401 invalid_session` | Pause drain, clear auth state (→ login screen); resume drain after re-authentication completes |
| `403 csrf_invalid` | Fetch fresh CSRF token from `GET /api/v1/sessions/current`; update mutation's `csrfToken`; retry once. If second attempt also fails, dequeue and log. |
| `409` or any 2xx | Treat as success (idempotent flag mutations) |
| Other 4xx | Dequeue and log (unrecoverable) |
| Network error | Stop drain; retry on next `online` event |

Drain is re-entrant-safe: a `draining` flag prevents concurrent runs.

#### Session-expiry flow

If drain receives `401 invalid_session`:

1. `offlineQueue.pause()` sets a `pendingDrain` flag on the queue (stored in `localStorage` as `tap:queue-pending:{userId}` boolean).
2. Auth state is cleared; `App.svelte` renders the login screen.
3. After successful login, `auth.bootstrap()` completes; `App.svelte`'s boot sequence calls `drain()` again, which picks up the queue.
4. The `pendingDrain` flag is cleared on successful drain completion.

This flow means a queue survives across logout/re-login cycles because it is keyed by user ID, not session ID.

#### Logout

`offlineQueue.clearForUser(userId)` deletes `tap:queue:{userId}` and `tap:queue-pending:{userId}` from `localStorage`. Called by `auth.logout()`.

### Warm-cache driver: `web/src/lib/warmCache.ts`

Exports one function: `warmCache(userId: number): Promise<void>`.

**Called from:**

1. `App.svelte` — 2 seconds after `auth.bootstrap()` resolves (deferred so it doesn't fight the initial render).
2. `App.svelte` — on the `online` DOM event, after `offlineQueue.drain()` completes.

**Algorithm:**

1. Fetch `GET /api/v1/entries?limit=50&unread=1`.
2. For each entry in the response, extract all `/api/v1/proxy/*` URLs from `content` using a regex (`/\/api\/v1\/proxy\/[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+/g`).
3. Cap extracted URLs per entry at 20 (guards against pathological entries with hundreds of images).
4. Deduplicate URLs across all entries.
5. Cap the total warm list at 200 URLs.
6. Fire `fetch(url, { cache: 'force-cache' })` for each URL. A `force-cache` fetch is a pure cache hit if the URL is already in the SW cache; a cold miss causes one round-trip to the Go proxy. This is deliberate — the warm-cache driver's job is to populate the cache, not just hit it.
7. Run fetches with concurrency 4 (matches the Go server's per-host default from concept §6.4).
8. Errors are swallowed silently — warm-cache failures must never surface to the user.

### PWA manifest

`vite-plugin-pwa` generates `web/dist/manifest.webmanifest` from config in `vite.config.ts`:

```json
{
  "name": "Tap",
  "short_name": "Tap",
  "description": "Self-hosted feed reader",
  "display": "standalone",
  "start_url": "/",
  "scope": "/",
  "background_color": "#fafaf7",
  "theme_color": "#002FA7",
  "icons": [
    { "src": "/icons/icon-192.png", "sizes": "192x192", "type": "image/png", "purpose": "maskable" },
    { "src": "/icons/icon-512.png", "sizes": "512x512", "type": "image/png", "purpose": "maskable" }
  ]
}
```

**`theme_color` coordination with M8:** The manifest value `#002FA7` (Klein Blue) is the static install-time value, corresponding to the light theme. M8 owns the dynamic `<meta name="theme-color">` update in `index.html` (or via JS) that follows the user's active theme at runtime — that controls the browser chrome color as the user switches themes without requiring a new manifest. M10 ships the static manifest; M8 owns the dynamic meta tag. The two do not conflict.

**Icons:** `icon-192.png` and `icon-512.png` follow the junction-dot motif from concept §12. Both are maskable (subject centered with safe-zone padding). These are the minimum required for PWA installability.

**`background_color`:** `#fafaf7` matches the light theme's background token from M8's design system.

### SPA wiring changes

#### `web/src/App.svelte`

```svelte
<script lang="ts">
  import { onMount } from 'svelte';
  import { auth } from './lib/auth';
  import { offlineQueue } from './lib/offlineQueue';
  import { warmCache } from './lib/warmCache';
  import { useRegisterSW } from 'virtual:pwa-register/svelte';

  const { needRefresh, updateServiceWorker } = useRegisterSW();

  onMount(async () => {
    await auth.bootstrap();
    if ($auth.user) {
      notifySWUser($auth.user.id);
      await offlineQueue.drain($auth.user.id);
      setTimeout(() => warmCache($auth.user.id), 2000);
    }
  });

  window.addEventListener('online', async () => {
    if ($auth.user) {
      await offlineQueue.drain($auth.user.id);
      warmCache($auth.user.id);
    }
  });
</script>

{#if $needRefresh}
  <div class="sw-update-banner">
    Update available —
    <button on:click={() => updateServiceWorker(true)}>Reload</button>
  </div>
{/if}

<!-- existing auth/route rendering unchanged -->
```

The `sw-update-banner` is fixed to the top of the viewport (`position: fixed; top: 0`), does not conflict with M8's mobile bottom tab bar.

#### `web/src/lib/auth.ts`

`auth.logout()` gains two new steps before clearing in-memory state:

1. `offlineQueue.clearForUser(userId)` — drops any pending offline mutations.
2. Post `{type: 'logout', userId}` to the SW via `navigator.serviceWorker.controller?.postMessage(...)` — triggers SW cache deletion for this user.

`auth.bootstrap()` after resolving with a live user posts `{type: 'set-user', userId}` to the SW.

#### `web/src/lib/api.ts`

`request()` wraps non-GET calls. When a network error is thrown (or `navigator.onLine === false`), instead of propagating the error to the caller it calls `offlineQueue.enqueue(userId, mutation)` and returns a synthetic "queued" result. The optimistic store update in the calling view already fired, so the UI is consistent.

The existing 401 handler (clears auth state) is unchanged for online failures. The queue's drain loop handles 401 on replayed mutations separately.

### Configuration

No new Go flags. No new environment variables. The SW registration, manifest generation, and icon paths are all build-time configuration in `vite.config.ts` and `web/package.json`.

New `vite.config.ts` additions:

```ts
import { VitePWA } from 'vite-plugin-pwa';

export default defineConfig({
  plugins: [
    svelte(),
    VitePWA({
      strategies: 'injectManifest',
      srcDir: 'src/sw',
      filename: 'sw.ts',
      registerType: 'prompt',  // shows update banner rather than auto-refreshing
      manifest: { /* as above */ },
      injectManifest: {
        injectionPoint: undefined,  // sw.ts handles precaching via workbox.precacheAndRoute
      },
    }),
  ],
});
```

`registerType: 'prompt'` is important — auto-refreshing the page while the user is reading an entry would be disruptive. The update banner lets the user choose when to reload.

## Out of scope (deferred)

## Cross-milestone notes

**M7 ↔ M10 (CSRF / session expiry):** The queue's CSRF token is current at enqueue time. Password change rotates the CSRF token (M6); on replay a `403 csrf_invalid` triggers a single re-fetch of the session to obtain the new token and retries once. A `401 invalid_session` pauses the drain and resumes after re-login. This design is documented in the coordinator notes and is a deliberate part of M10's scope.

**M8 ↔ M10 (theme_color, update banner):** M8 provides theme tokens and owns the dynamic `<meta name="theme-color">` update. M10's manifest uses the static Klein Blue value. The SW update banner is fixed to the top viewport edge to avoid collision with M8's mobile bottom tab bar.

**M9 ↔ M10 (OPML import):** `POST /api/v1/opml` is a POST — the SW does not cache POST responses. `GET /api/v1/search*` is explicitly excluded from the stale-while-revalidate pattern. Both fall out naturally from the SW's URL-pattern matching.

**M10 ↔ M3 (proxy cache):** Proxy URLs are deterministic per source URL (M3 token design). The SW cache-first strategy layers on top of M3's Go-side FS cache. A URL evicted from the Go FS cache will cause a Go-side origin re-fetch on the next SW miss — no SW-side change needed.

**M7 ↔ M10 (per-user isolation):** SW cache names and `localStorage` keys are suffixed with the user ID. Logout clears both. If two users share a browser, their caches are isolated and only the logged-out user's data is cleared.

## Tests and methodology

M10 follows the test-first discipline of M1–M9. Pure scaffolding (Vite config additions, icon files, manifest JSON) is exempt. Everything with branches, error handling, or state is in scope.

### Unit tests (vitest)

**`web/src/lib/__tests__/offlineQueue.test.ts`**

- `enqueue` writes to `localStorage` keyed by user ID.
- `enqueue` preserves insertion order; `drain` processes mutations serially in order.
- `drain` dequeues on 2xx response.
- `drain` on `401`: sets `pendingDrain` flag, stops draining, does not dequeue.
- `drain` on `403 csrf_invalid`: re-fetches session, updates `csrfToken`, retries; if retry also 403, dequeues and continues.
- `drain` on network error: stops; next call to `drain` retries from the failed mutation.
- `drain` on 4xx other than 401/403: dequeues and continues.
- `clearForUser` removes only that user ID's keys; another user's queue is unaffected.
- Queue survives simulated reload: serialize queue to `localStorage`, construct a fresh `offlineQueue` instance, call `drain`, assert mutations are replayed in order.
- `draining` flag prevents concurrent drain calls.

**`web/src/lib/__tests__/warmCache.test.ts`**

- Extracts proxy URLs from entry `content` using the regex.
- Respects per-entry cap of 20 URLs.
- Respects total cap of 200 URLs across all entries.
- Deduplicates URLs before fetching.
- Fires fetches with `cache: 'force-cache'`.
- Runs at concurrency 4 (assert no more than 4 in-flight at once).
- Swallows fetch errors silently.
- No-ops gracefully when the entries response is empty.

### Service worker strategy tests (vitest, `@types/service-worker`)

- Cache name for entry-list routes is `tap-api-{userId}`.
- Cache name for proxy routes is `tap-proxy-{userId}`.
- `/api/v1/proxy/*` pattern matches proxy URLs, does not match entry-list URLs.
- `/api/v1/entries*` matches entry-list URLs, does not match proxy URLs.
- `/api/v1/search*`, `/api/v1/opml`, `/api/v1/sessions*` are not matched by any caching strategy.
- POST/PATCH/DELETE requests are not matched by any caching strategy.

### PWA manifest test (vitest)

- The generated `manifest.webmanifest` contains `name`, `display: standalone`, `theme_color: #002FA7`, and icons at 192×192 and 512×512 with `purpose: maskable`.

### End-to-end offline tests (Playwright)

Two scenarios using `page.context().setOffline(true/false)`.

**Scenario 1 — Offline reading:**

1. Load app, log in, let unread list render and warm-cache run.
2. Open one entry (reader view renders and is in SW cache).
3. `setOffline(true)`.
4. Reload the page.
5. Assert app shell loads (precached `index.html`).
6. Navigate to the entry. Assert body renders (stale-while-revalidate hit).
7. Assert proxied images render (cache-first hit).

**Scenario 2 — Offline mutation replay:**

1. Load app, log in.
2. `setOffline(true)`.
3. Open an entry; assert auto-mark-read fires and the mutation is enqueued (check `localStorage` for `tap:queue:{userId}`).
4. Toggle saved on another entry; assert queued.
5. `setOffline(false)`.
6. Wait for drain to complete (assert `tap:queue:{userId}` is empty in `localStorage`).
7. Fetch `GET /api/v1/entries/{id}` directly and assert `read: true` and `saved: true` on the server.

**Scenario 3 — Queue survives reload:**

1. Load app, log in.
2. `setOffline(true)`.
3. Mark an entry read; assert queued in `localStorage`.
4. Reload the page while offline.
5. `setOffline(false)`.
6. Wait for drain; assert the mutation was replayed.

The Playwright ARM64 chromium symlink (`/opt/google/chrome/chrome`) is already in place per project memory.

## Definition of done

1. `make test` passes (`go test ./... -race`; no new Go code so this is a regression check only) and `pnpm --dir web test` passes including the new unit tests.
2. `pnpm --dir web run check` passes (svelte-check + TypeScript).
3. `make build` produces a static binary whose embedded `web/dist` contains `sw.js`, `manifest.webmanifest`, and `icons/icon-{192,512}.png`.
4. In Chrome/Chromium: the app is installable (no PWA install errors in DevTools Application tab); the manifest fields and icons pass the PWA checklist.
5. With DevTools → Network → Offline: the app shell loads, the unread list renders from cache, a previously opened entry renders including its proxied images.
6. With DevTools → Network → Offline: marking an entry read enqueues the mutation in `localStorage`; going back online drains the queue; the server reflects the change.
7. Three Playwright offline scenarios pass (see Tests above).
8. Logout clears the SW caches for that user and the `localStorage` queue.
9. A second user logging in on the same browser has an empty queue and separate cache namespaces.

## What this milestone deliberately does not prove

- That background sync via the `SyncManager` API works — not shipped.
- That push notifications work — not shipped; no hosted backend.
- That the dynamic `<meta name="theme-color">` updates on theme switch — M8 owns this.
- That the archival sweep interacts correctly with the SW cache — M11 owns archival.
- That OTel traces cover SW → Go round-trips — M12 owns observability.

If you find yourself adding `SyncManager` background sync, push notification support, per-user SW admin tooling, or a custom offline indicator widget beyond the `needRefresh` banner, push back. M10's job is the smallest offline-first layer that makes Tap usable without the Go server, with clean seams for M8 (dynamic theme-color) and M11 (archival sweep) to plug into.
